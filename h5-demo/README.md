# KAKA 家庭物资 · H5 演示

家庭物资 ERP（药品 / 食品登记、效期、批次）的移动端网页演示。
技术栈只有 **Vite + TypeScript**，不引框架、不引状态库、不引请求库 ——
五个视图、几十个 DOM 节点，手写 `h()` 比装一套 React 更省事，
也更容易看清「一个 C 端页面到底需要后端提供什么」。

## 快速开始

```bash
# 1) 后端（另开一个终端，在 backend 目录下）
.venv/Scripts/python.exe main.py run --env=dev      # 监听 127.0.0.1:8001

# 2) 演示数据（首次必跑；提供分类树/属性模板/演示账号 + 20 条药品食品）
PYTHONUTF8=1 PYTHONIOENCODING=utf-8 .venv/Scripts/python.exe app/plugin/module_app/erp/tests/seed_demo.py

# 2b) 可选：再给三个家庭各灌 8 条「形态不齐」的物资（未归类、零批次、已耗尽、
#     无有效期、今天到期、私密物品、两个录入人），用来把列表和详情的边角状态撑满
PYTHONUTF8=1 PYTHONIOENCODING=utf-8 .venv/Scripts/python.exe app/plugin/module_app/erp/tests/seed_households.py

# 3) 本演示（在 h5-demo 目录下）
npm install
npm run dev                                          # 打开 http://127.0.0.1:5173
```

## 目录与职责

```
index.html          只放一个 <div id="app">，全部内容由 JS 渲染
vite.config.ts      开发代理：/api → http://127.0.0.1:8001（见下文「为什么不用管 CORS」）
src/main.ts         入口：装配视图、注入 401 回调、按登录态决定首屏
src/api.ts          唯一发请求的地方：信封拆包 / 令牌续期 / 家庭头，都挡在这一层
src/types.ts        后端 Pydantic Schema 的 TS 镜像（字段与可空性和后端一致）
src/store.ts        会话状态（localStorage 持久化）：令牌、会话 ID、用户、家庭列表、当前家庭
src/session.ts      跨视图共享的会话动作：刷新家庭列表、退出登录
src/router.ts       nav.xxx() 跳转 + main.ts 注入实现，用来解开视图间的循环依赖
src/ui.ts           h() 构建 DOM、toast / 确认框 / 底部菜单 / 弹窗表单、日期与金额格式化
src/style.css       全部样式（CSS 变量定义配色，移动端优先）
src/views/login.ts  登录页：密码登录 / 注册 / 短信登录 三个 Tab
src/views/list.ts   物品列表（首页）：搜索、分类筛选、分页、家庭切换、扫码入口
src/views/form.ts   录入 / 编辑：基础字段 + 分类驱动的扩展属性 + 图片 + 首批批次
src/views/detail.ts 详情：档案、扩展属性、批次增删改、物品编辑与删除
src/views/profile.ts 个人中心：账号资料与头像、我的家庭、改密码、在线设备、退出登录
```

## 后端约定的几处细节

**响应信封**：后端所有接口都包一层 `{ code, msg, data, success }`。
`api.ts` 负责把 `data` 掏出来，`success === false` 或非 2xx 时把中文 `msg`
变成 `ApiError` 抛出 —— 所以视图里只有一句 `catch { toast(error.message) }`。
FastAPI 的 422 校验错误 `detail` 是数组，也在这里统一拍平成一句人话。

**登录令牌**：请求带 `Authorization: Bearer`；401 且有 refresh_token 时静默换新并重放一次，
刷新也失败才清会话回登录页。并发请求同时 401 时共用同一个刷新 Promise，
否则会各自创建会话、互相把对方的令牌作废（表现为「刚刷新完又是 401」）。

**家庭上下文**：`family: true` 的接口自动带 `X-Family-Id` 头。
一个人可以属于多个家庭，所以 `family_id` 刻意不进 JWT，切家庭不用重新登录。
缺头后端回 400，非成员或家庭停用回 403。

**扩展属性**：物品表单里那组「跟着分类变」的字段来自 `/erp/attr/schema/{category_id}`
（含从祖先分类和全局模板的继承）。提交前按模板类型转换值
（number→数字、date→`YYYY-MM-DD`、multi_select→字符串数组），
模板之外的键后端会直接丢弃，所以前端不必也无法「塞私货」。

**图片上传**：`/erp/item/upload` 只要求登录、不带家庭头（图片先传、物品后建是常见顺序）。
返回的绝对 URL 由 `request.base_url` 拼出，因为代理开了 `changeOrigin`，
这个 URL 指回 8001，`<img>` 能直接加载。

**个人中心那几个接口**：`/login/profile/*` 与 `/login/sessions` 只认登录态、不带家庭头。
改密码的长度与复杂度规则完全由后端配置（`PASSWORD_MIN_LENGTH`、强度开关，都可在 env 里改），
前端刻意不复制一份校验，报错直接用后端返回的中文 —— 两边各写一套规则迟早口径分叉。
改密成功后后端保留当前会话、作废其余会话；「退出其他设备」同理用令牌里的 session id 判定「本机」，
所以前端不需要（也拿不到）当前会话 ID 就能保证不会把自己踢下线。

**为什么不用管 CORS**：开发期 `/api` 由 Vite 代理转发，浏览器视角前后端同源，
预检请求根本不会发生。生产部署时把 `dist/` 和后端放同一域名下同样不需要放开跨域。

## 已验证过的路径

密码登录 / 注册（含短信验证码）/ 退出登录；家庭列表、创建家庭、邀请码加入、切换家庭、无家庭空态；
物品分页、关键词搜索、分类筛选、扫码命中跳详情与未命中带条码进新建、
新增（图片上传 + 扩展属性 + 首批批次）、编辑、删除；批次新增 / 修改 / 删除；
个人中心改昵称与性别、换头像、改密码（含「两次不一致」「原密码错误」两条失败路径）、
在线设备列表与「本机」标记、退出其他设备登录、从个人中心退出后重新登录；
三个家庭之间切换后的按人裁剪列表（成员看不到户主「仅本人可见」那条，户主作为管理员能看全家庭）、
以及这些边角状态在列表和详情里的渲染：未归类、零批次、批次已耗尽、有效期为空、
今天到期、已过期 N 天、小数剩余量（`1.50 组`）、私密标签、跨家庭同名物品、两种录入人。

## 已知限制（演示项目刻意不做）

- **未归类物品没有筛选入口**：顶部的分类 chip 全部来自分类树，而 `category_id` 查询参数只支持
  「等于某个分类」，没有「未归类」这一档。未归类的物品只在「全部」和搜索结果里出现。
- **编辑时清空输入框不会把字段改回 NULL**：后端 update 是 `exclude_unset + exclude_none` 语义
  （见 `login/user/service.py` 的 `update_profile`），空值一律不参与更新 ——
  连显式传 `"avatar": null` 也会被丢掉。落到界面上就是：个人中心的邮箱只能改不能清，
  头像一旦上传就摘不掉（要清得后端先设计一套「显式置空」的口径）。
- **没有 URL 路由**：只有 5 个视图，浏览器前进/后退不是验收项，状态放在各视图闭包里。
  刷新页面会回到列表首页。
- **会话放在 localStorage**：够用且刷新不掉线；有效性最终由后端 Redis 判定。
  真实项目要按需换 httpOnly Cookie，避免 XSS 能直接读令牌。
- **没有虚拟列表 / 骨架屏**：单家庭物品上限不高，一屏 20 条直接渲染。

## 想调整种子数据

改 `backend/app/plugin/module_app/erp/tests/seed_demo.py` 里的 `ATTR_TEMPLATES` / `ITEMS` 后重跑即可：
脚本按「名称 / (分类, code)」复用已有数据，重复跑不会堆重复行，
但**已存在的物品会被跳过而不是覆盖**。要让改动落到那 20 条物品上，需要加 `--reset`
重灌 —— 它会把「演示家庭」里的物品软删除后重新录入，
所以手工在页面上改过的演示数据会丢，跑之前先确认一下。

`seed_households.py`（三个家庭各 8 条「不齐」的数据）思路一样，但有两个坑值得先知道：

- **批次「已耗尽」不能在建档时一次写完**：后端建批次时状态固定写 `在用`，
  耗尽是用完之后的动作，所以脚本建完物品再补一次 `PUT /erp/item/batch/update/{id}`。
  补的时候**不能按提交下标对位** —— 批次列表是「新买的排前面」返回的，
  和提交顺序正好相反，按下标会把没耗尽的那批标掉。脚本改用「进货数量 + 有效期」匹配。
- **列表里的「N 批」和「剩余库存」只统计在用批次**，所以「真的一条批次都没录」和
  「批次全部耗尽」在列表上长得一样（都是 `0 盒 · 0 批`），要区分得点进详情看批次状态。

它的 `--refresh` 比 `seed_demo.py --reset` 温和：只软删「名称在这 24 条清单里、
且归属人是那两个演示账号」的物品，`seed_demo` 的 20 条和你手工加的数据都不会被碰
（同名但不是演示账号录的会打一行 `[保留]` 跳过）。

脚本只增不删：把 `ATTR_TEMPLATES` 改小之后，旧库里多出来的模板还得手动删
（后台 `DELETE /api/v1/app/erp/admin/attr/delete`，body 传 ID 数组，软删除），
否则详情页会多出一条取不到值的空属性。
